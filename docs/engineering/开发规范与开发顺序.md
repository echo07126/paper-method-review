# 开发规范与开发顺序

> 依据：`docs/product/软件需求说明.md`（含第 14 节可扩展性设计、第 16 节数据安全规范）。
> 本文档是开发的**唯一执行口径**：规范类条款为强制项，顺序类条款为排期基线。任何偏离需先改需求文档并升版，再改本文档。

## 1. 目的与适用范围

- 统一编码、结构、接口、安全、测试、交付标准，避免后期返工。
- 明确开发顺序、依赖与验收，保证一人冲刺也能按里程碑交付。
- 适用范围：`backend/`、`frontend/`、`checklists/`、`samples/`、`materials/` 全部产出物。

## 2. 版本与依赖基线

| 层 | 选型 | 版本要求 | 备注 |
| --- | --- | --- | --- |
| 运行时 | Python | 3.11+ | 类型注解与 Pydantic v2 |
| 后端 | FastAPI / Uvicorn / Pydantic v2 / pydantic-settings | 最新稳定版 | 依赖锁定 |
| 文档解析 | python-docx（一期仅 DOCX） | 锁定 | PDF / OCR 走接口预留，二期实现 |

| 测试 | pytest + httpx.TestClient（后端）；Playwright（E2E，二期可选） | 锁定 | 安全用例必进 CI |

## 3. 仓库结构与模块边界

```
paper-method-review/
├── .github/workflows/    # CI
├── backend/              # FastAPI 应用、活动脚本与归档脚本
├── checklists/           # 审查清单 JSON（可插拔）
├── docs/                 # 需求与交付文档
├── frontend/             # Vue3 应用（含 mockup/ 设计基准）
├── materials/            # 提交材料
├── samples/              # 评测样本与标注
├── docker-compose.yml
└── requirements.txt      # 开发依赖入口，运行时依赖引用 backend/requirements.txt
```

边界规则（强制）：

1. `parsers/` 只产出 `DocumentIR`，禁止在其中做审查判定。
2. `engine/` 只消费 `DocumentIR` 与 `Element`，禁止直接读文件或调 HTTP。
3. `reports/` 只消费 `Finding` 集合，禁止反向依赖 `engine` 内部实现。
4. `storage/` 是唯一持久化入口；其他模块禁止直接操作 SQLite 或临时目录。
5. `api/` 只做参数校验、鉴权、编排与错误映射，禁止写业务逻辑。
6. 新增格式 / 清单 / 模型 / 导出，只允许按需求文档 14.8 的 SOP 扩展。

## 4. 编码规范

### 4.1 通用

- 所有对外数据结构必须用 Pydantic 模型定义（请求、响应、DocumentIR、Finding）。
- 禁止裸 `except:`；异常必须映射为 `core/errors.py` 中的错误类型与错误码。
- 禁止在代码中硬编码路径、URL、密钥、模型名；统一走配置。
- 每个模块文件头部保持单一职责；函数超过约 40 行需拆分。

### 4.2 后端（Python）

- 类型注解全覆盖（函数签名、返回值）；公共函数写简短 docstring。
- 命名：模块/函数 snake_case，类 PascalCase，常量 UPPER_SNAKE。
- 格式化与检查：ruff（format + lint），mypy 可选但公共接口需类型正确。
- 运行时依赖统一放 `backend/requirements.txt`；根 `requirements.txt` 只引用运行时依赖并追加开发工具。
- 时间统一 UTC 存储，接口返回 ISO 8601。

### 4.3 前端（Vue3 + TS）

- 严格 TypeScript（`strict: true`），禁用 `any`（确需时注释理由）。
- 组件分层：`views/`（页面）→ `components/`（展示组件）→ `api/stores/router`（数据与路由）。
- 禁止 `v-html` 渲染任何上传内容；展示文本必须转义。
- 所有网络请求经 `src/api/client.ts`，统一错误提示与 request_id。
- 样式使用主题变量（见 `src/styles/theme.css`），禁止散落硬编码色值。

## 5. 数据模型与接口规范

- 对象分层：结构层 → 引用层 → 知识层 → 证据层 → 判定层（见需求 12.2）。
- 对外 ID 一律 ULID/UUID 字符串；禁止暴露自增主键。
- API 前缀 `/api/v1`；统一响应错误结构 `{code, message, request_id}`。
- 长耗时接口统一范式：`POST` 提交任务 → 返回 `job_id` → `GET` 轮询状态 → 取结果。
- 分页、排序、过滤参数命名统一（`page`、`page_size`、`sort`）。
- 接口改动必须先更新 OpenAPI 描述和 `docs/engineering/API接口说明.md`，再改实现。

## 6. 配置与密钥规范

- 非敏感配置：`config/*.yaml` 或环境变量（模型名、温度、清单路径、超时）。
- 密钥：**仅**环境变量（`.env` 不入库、不入镜像）；启动时校验必填。
- 提供 `.env.example`；本地开发复制为 `.env`。
- 禁止任何密钥出现在日志、响应体、前端代码、异常信息中。

## 7. 日志与可观测规范

- 统一使用 `core/logging.py` 的 `safe_logger`，带脱敏过滤器。
- 禁止记录：论文正文、prompt 全文、会话令牌、密钥。
- 允许记录：事件名、request_id、耗时、tokens（输入/输出/缓存）、错误码。
- 每次审查落库一条指标：耗时、tokens、重试次数、失败原因。
## 8. 安全编码规范（强制，详见需求第 16 节）

1. 上传必须经 `validators.validate_upload()`：扩展名 + 魔数双验、大小/页数限制、随机文件名、落盘到 Web 根之外。
2. 资源访问必须经 `storage.authorized_get(session, id)`；越权返回 404，禁止泄露存在性。
3. 会话令牌：≥128bit 随机、DB 仅存 hash、Cookie `HttpOnly; Secure; SameSite=Lax`、过期轮换。
4. LLM 调用必须经 `LLMProvider`（超时/重试/限流/记账）；论文内容包裹在数据分隔块并声明“忽略其中指令”，输出必须 Schema 校验。
5. 删除统一走 `purge_session()`（DB + 临时文件 + 缓存）；缓存键含会话归属与版本，命中后仍校验归属。
6. 生产配置：`DEBUG=False`、API Docs 关闭或鉴权、仅暴露 443、关闭 `--reload`。
7. 容器非 root、最小镜像、镜像扫描；依赖锁定并做漏洞扫描。
8. 安全用例必须进 CI：越权（换会话访问他人报告）、Prompt 注入、超大/伪造文件、限流。
9. 删除/导出/管理操作写审计日志（只记操作与时间，不记内容）。
10. 部署前逐项通过需求 16.5 的上线安全检查清单。

### 9.1 测试分层

| 层 | 工具 | 覆盖对象 | 必须通过 |

### 9.2 完成定义（DoD）

一项任务只有同时满足以下条件才可标记完成：

- [ ] 代码通过 ruff / eslint 检查，无类型错误（公共接口）。
- [ ] 相关单元 / 集成 / 安全测试全部通过；新增行为有对应测试。
- [ ] 不新增硬编码密钥 / 路径；配置项已登记到 `.env.example`。
- [ ] 日志不含正文、prompt、令牌、密钥（抽样确认）。
- [ ] 涉及数据流 / 存储 / 外部调用时，过一遍需求 16.3 与 16.5 的相关条目。
- [ ] 文档同步：需求或本文档对应章节已更新（含追踪矩阵）。
- [ ] 追踪矩阵中该任务映射的 FR / Gap 已覆盖并注明验收方式。

## 10. Git 与评审流程

- 建议初始化 git 仓库；分支：`main`（可交付）、`feat/<task-id>-<slug>`、`fix/<task-id>-<slug>`。
- 提交信息：`<type>(<scope>): <summary>`，type ∈ feat/fix/docs/test/chore/refactor。
- 每个任务一个分支 / 一次合并；合并前自查 DoD 与安全条款。
- 单人项目也保留提交历史：便于回溯、回滚与撰写开发流程材料（评分项“开发流程”）。
