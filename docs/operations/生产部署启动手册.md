## 1. 部署前准备

### 1.1 服务器要求

| 项 | 要求 | 说明 |
| --- | --- | --- |
| 操作系统 | Linux（Ubuntu 22.04 / Debian 12 或同类） | 容器化部署，发行版不敏感 |
| CPU / 内存 | 2 核 4GB 起步 | 规则模式毫秒级；含模型顾问单篇 9–40 秒。单机单 worker，模型并发由 `LLM_MAX_CONCURRENCY`（默认 4）与限流约束，横向扩容前需共享存储 + 网关级限流 |
| 磁盘 | ≥ 20GB | `data/`（SQLite + 临时文件）+ 镜像 + 日志 |
| Docker | 24+ 与 Docker Compose v2 | `docker --version`、`docker compose version` |
| 域名 | 1 个，A 记录指向服务器 | TLS 需要 |

### 1.2 需要提前准备的输入

- [ ] 域名（例如 `review.example.com`）
- [ ] 生产 DeepSeek API Key（**独立创建，不复用开发 Key**）
- [ ] 备份目标（对象存储 / 另一台机器的目录 / 加密卷）
- [ ] 告警渠道（邮件 / 企业微信 / 钉钉 Webhook）

## 3. 配置（最关键的一步）

### 3.1 创建生产环境变量文件

```bash
cd paper-method-review
cp backend/.env.example backend/.env
chmod 600 backend/.env          # 仅属主可读
```

### 3.2 必须修改的项

```ini
# backend/.env
APP_ENV=prod                 # 触发生产配置守卫（禁止 DEBUG/Docs，启动即校验）
DEBUG=false
DOCS_ENABLED=false           # 生产关闭 API 文档
ALLOWED_ORIGINS=https://review.example.com   # 不要用 *；与凭据 Cookie 同用会被拦截

DEEPSEEK_API_KEY=sk-<生产专用 Key>
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-flash   # DeepSeek-V4.1-Flash；原生支持视觉输入，二期 L3 图像识读复用同一模型，无需换 Provider

SESSION_TTL_HOURS=2
DATA_RETENTION_HOURS=2       # 保留期下限，实际取 max(SESSION_TTL, 该值)
MAX_UPLOAD_MB=50
MAX_PAGES=60

LLM_MAX_CONCURRENCY=4        # 全局模型并发信号量；按服务商账号配额与机器核数调整（过大易触发 429）
```

### 3.3 配置自检（不启动服务也能验）

```bash
# 合规配置应打印"通过"；任何 prod + DEBUG/Docs 组合会直接报错
cd paper-method-review/backend && python -c "
from app.core.config import Settings
Settings(app_env='prod', debug=False, docs_enabled=False, allowed_origins='https://review.example.com').guard_production()
print('生产配置守卫：通过')
"
```

> `guard_production()` 在 `APP_ENV != dev` 时若发现 `DEBUG=true` 或 `DOCS_ENABLED=true`，**应用启动即失败**——这是刻意设计，防止误配。

## 4. 启动

### 4.1 构建并启动

```bash
cd paper-method-review
docker compose up -d --build
docker compose ps
```

预期：`backend` 与 `frontend` 均为 `Up`，且健康状态变为 `healthy`（compose 已配置 healthcheck；
前端探针 `/healthz`、后端探针 `/api/v1/health`）。

### 4.2 本机自检（未开放公网前）

```bash
curl -s http://127.0.0.1:8000/api/v1/health
# {"status":"ok","app_env":"prod","docs_enabled":false}

curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/healthz
# 200

curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/
# 200（SPA index.html）
```

### 4.3 关键行为确认（建议留档）

| 检查 | 命令 / 方法 | 期望 |
| --- | --- | --- |
| API Docs 已关闭 | `curl -o /dev/null -w '%{http_code}' http://127.0.0.1:8000/docs` | `404` |
| Cookie 安全属性 | 上传后看响应头 `Set-Cookie` | 含 `HttpOnly`、`Secure`、`SameSite=Lax` |
| 定期清理任务在跑 | `docker compose logs backend \| grep periodic_cleanup` | 有 `periodic_cleanup started interval=300s` |
| 错误不泄露细节 | 访问不存在的报告 | `{"code":"not_found", ..., "request_id":"..."}` |
| 越权拦截 | 用另一个会话访问他人报告 ID | `404` |

> 注：`Secure` Cookie 只在 HTTPS 下会被浏览器回传，因此**本机用 http 自测时登录态看似失效，这是预期行为**；
> 公网必须走 HTTPS（见 §5）。生产路径已实测：https 下上传→审查→取报告全链路 200。

## 5. 对外暴露（TLS 与跳转）

Compose 只绑定 `127.0.0.1`，公网入口由前置 Nginx / 云负载均衡承担。

### 5.1 Nginx 反向代理 + 证书

```bash
sudo apt-get update && sudo apt-get install -y nginx certbot python3-certbot-nginx
sudo certbot --nginx -d review.example.com
```

站点配置要点：

```nginx
server {
  listen 80;
  server_name review.example.com;
  return 301 https://$host$request_uri;      # HTTP 强制跳转
}

server {
  listen 443 ssl;
  server_name review.example.com;

  ssl_certificate     /etc/letsencrypt/live/review.example.com/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/review.example.com/privkey.pem;

  # HSTS：仅在 HTTPS 确认正常后开启（localhost 演示环境切勿开启）
  add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

  client_max_body_size 60m;                   # 与后端 MAX_UPLOAD_MB=50 匹配
  proxy_read_timeout 180s;                    # 覆盖含模型顾问的最长审查耗时

  location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto https;
  }
}
```

### 5.2 验收

```bash
curl -I  http://review.example.com    # 301，Location: https://...
curl -I  https://review.example.com   # 200，含 Strict-Transport-Security
```

> `frontend/nginx.conf` 中已备好一行注释形式的 HSTS 开关，供容器内自终止 TLS 的场景使用。

## 6. 安全加固

### 6.1 安全组（云控制台）

| 端口 | 来源 | 用途 |
| --- | --- | --- |
| 443 | 0.0.0.0/0 | 唯一对外入口 |
| 80 | 0.0.0.0/0 | 仅用于 301 跳转 |
| 22 | 仅你的 IP / 跳板机 | SSH |

```bash
# 服务器上确认没有意外监听
ss -lntp
# 预期：只有 80/443（nginx）与 127.0.0.1:8000/8080（compose）
```

### 6.2 密钥管理

- 生产 Key **独立创建**，不复用开发 Key（开发 Key 若曾出现在聊天记录/截图，立即吊销）。
- `backend/.env` 权限 `600`，且已被 `.gitignore` 与 `.dockerignore` 排除（不会进镜像/仓库）。
- 建立 90 天轮换日历；轮换采用"新 Key 生效 → 重启 → 验证 → 吊销旧 Key"。

### 6.3 数据留存与删除传播

```bash
# 删除传播 + 备份演练（隔离环境运行，不触碰真实 data/）
python backend/scripts/backup_check.py --backup-dir /var/backups/pmr --create-backup
```

预期输出 `BACKUP CHECK PASS`，且会打印：purge 后 `sessions/documents/reports/jobs/chat_messages` 五张表与临时目录全部清空；
快照内仍保留 purge 前的 1 条会话与其结构化正文——**这正是备份侧必须独立做删除传播的证据**。

> 一期策略：**默认不备份数据库**（正文仅在会话内暂存）。若业务要求留存报告，则必须加密备份，
> 并把删除请求传播到备份侧（在上线待办第 4 项登记策略）。

## 7. 日志、监控与演练

### 7.1 日志

- 应用日志走 stdout → 容器日志；compose 已配置 `json-file` 驱动，`max-size=10m`、`max-file=30`（约 ≤30 天）。
- 日志已脱敏（密钥/令牌/正文），`RedactionFilter` 由 `security_audit.py` 取证。

```bash
docker compose logs -f backend | grep -E 'llm_unavailable|rate_limited|internal_error'
```

### 7.2 监控指标（建议至少采集）

| 指标 | 来源 |
| --- | --- |
| 5xx 比例 | nginx access log / 错误码 |
| 429 限流次数 | 日志 `rate_limited` |
| 模型失败率 | 日志 `llm_unavailable` |
| 单篇审查耗时 / token | 日志 `review_done` |
| 磁盘使用率 / SQLite 大小 | 主机监控 |
| 容器健康状态 | `docker compose ps` / healthcheck |

### 7.3 演练（上线前至少各一次）

1. **密钥泄漏**：吊销 → 换新 Key → 重启 → 验证。
2. **被刷**：确认限流生效（上传 20/min、审查 10/min、追问 120/min，会话 + IP 双桶），观察 429。
3. **误删**：调用 `POST /api/v1/sessions/purge` → 用 `backup_check.py` 确认删除传播彻底；
   若启用备份，演练一次恢复。

## 11. 故障排查

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 启动即报"配置不合规" | prod 下 `DEBUG=true` 或 `DOCS_ENABLED=true` | 改 `.env` 后重启（见 §3.3） |
| 上传后登录态丢失 | 走了 HTTP（`Secure` Cookie 不回传） | 必须 HTTPS；确认 301 跳转生效 |
| 审查接口 404 | 会话 Cookie 未带上 | 检查 `ALLOWED_ORIGINS` 与域名一致、浏览器未跨域 |
| 报告打开提示"已清除" | 会话已过期（默认 2h） | 预期行为；重新上传审查 |
| 模型相关条目全是"存疑" | Key 未生效 / 调用失败 | 看日志 `llm_unavailable`；规则结果不受影响 |
| 磁盘持续增长 | 清理任务未跑 | `grep periodic_cleanup`；必要时按 §10 手动清理 |
| 413 上传失败 | 超过 `MAX_UPLOAD_MB` 或解压体积/页数超限 | 调整配置或提示用户拆分文档 |
