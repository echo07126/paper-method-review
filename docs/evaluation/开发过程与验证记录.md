### W3 评测结论（5 篇样本 / 24 条标准答案）
- 仅规则：检出率 **16/24 = 67%**、精确率 **100%**；自建样本 14/14（100%），真实样本 2/10（漏项集中在语义类 R-03/R-04/R-08/R-14/R-15）。
- 规则 + LLM：检出率仍 67%、精确率降至 **70%**（LLM 未补上语义漏报——被证据门控降级为“存疑”；同时新增 R-04/R-06/R-12/R-07/R-10 等误报）。
- 结论：当前 LLM 既未提升召回又损伤精确率，因此 W3 调优优先级调整为——
  1. **规则扩条目**：把「缺失描述型」检查确定性化（R-03 无划分说明、R-04 无基线、R-08 多重比较、R-14 无种子、R-15 无局限），预计可大幅提升召回；
  2. **要素词表补齐**：为基线、局限、多重比较、划分说明等补充要素，使证据门控能给语义判定挂锚点，避免误降级；
  3. **规则前置否决**：规则对某条目判定“通过”时，LLM 不得再报问题，用于收敛误报；
  4. 完成后再跑 `eval_ac.py --llm` 与 `consistency_check.py`，目标检出率与精确率均 ≥90%。

结论（重要）：**LLM 语义判定目前无法稳定达到目标**，确定性规则才是可信基座。已落地的达标做法：
- 规则覆盖扩展到全部条目（R-02/03/05/07/08/09/14/15 + 引用类），并对可判定条目输出 problem/pass；
- **规则前置否决**：规则判定“通过”的条目，LLM 不得报问题；
- **顾问模式**：LLM 结论一律降级为「建议/存疑」（不计入问题数），仅作人工复核线索；
- 引文验证（逐字引用 + 条目关键词闸门）用于把模型结论落到原文；
- 锚点定位按“信号所在段落”选取（R-03/08/14 取相关段、R-15 取末段），AC-3 从 62% 提升到 91%。
1. **规则扩覆盖（主路径）**：把 R-04 基线数量、R-08 多重比较、R-10 重复/方差、R-13 预处理、R-15 局限等改为「存在/缺失」确定性判定；
2. **LLM 定位调整为“建议”**：LLM 结论默认进入「存疑/建议」区，只有引文验证通过才计入 problem；
3. **清单判定准则对齐**：为每条清单写明「可判定标准」，无法客观判定的条目标注为 advisory，不计入 AC-2 分母；
4. 完成后重跑评测，目标检出率与精确率均 ≥90%。

### 工程加固（2026-09-22）：数据生命周期、配置隔离与门禁
- **运行期定期清理**：原来 `cleanup_expired` 只在应用启动时执行一次，服务连续运行超过会话 TTL（默认 2h）后过期数据不再回收，与「会话过期自动清除」的对外口径不符。新增 `app/storage/cleanup_task.py` 常驻协程（每 300s 一轮），在 `main.lifespan` 启动时先清一次、退出时优雅取消；同时把孤儿临时目录（进程被杀导致的泄漏）一并回收。

### 修改对比页默认「先生成修改稿」+ 消除重复审查与并发上限失真（2026-10-11）
- **问题现象 ①（对比无变化）**：完成审查后进入「修改前后对比」，左右两侧问题清单完全一致，看起来「报告没改稿、对比无变化」。
- **根因 ①**：`CompareView.vue` 的 `onMounted` 会把「修改后」下拉框默认预选为**另一份已存在报告**（`data.find(id !== beforeId)`）。只要会话里已有 ≥2 份报告（例如上次对比已生成过修改稿），页面就直接拿**两份既有报告互比**并带 `use_llm=false`，**跳过「生成修改稿 + 二次审查」这条主线**；而这两份报告通常来自同一份未修改的文档，故问题集相同、零差异。副作用：生成用复选框「用模型结合全文生成补写」带 `v-if="!afterId"`，一旦 `afterId` 被预选，该选项根本不出现（用户侧反馈「没有这个选项」），进一步印证生成路径被跳过。
- **问题现象 ②（进入对比即全系统卡顿）**：点进「修改前后对比」后，整站响应变慢、报告页长时间转圈；怀疑对比页过度占用模型。
- **根因 ②（两处浪费 + 一处上限失真）**：
  1. **初稿被重复审查**：`routes_compare.compare` 先从存储取回初稿报告 `before`，又调 `review_and_compare`，后者内部**再跑一遍完整的初稿审查**并把结果丢弃（`review_and_compare` 的返回值第一位被 `_` 接收）。对比因此多付**一次完整审查**（含视觉识读 + 定向送审）的模型开销。`routes_report.revise_report` 同样丢弃已取回的报告、重复审查。
  2. **视觉识读被跑两遍**：修改稿只改 `paragraphs`，`document.images` 不变，二次审查仍会对同一批图重跑识读（受 `LLM_VISION_MAX_IMAGES` 限制）。此项**保持现状未改**（跳过会改变二次审查的存疑线索口径）。
  3. **`LLM_MAX_CONCURRENCY` 实际不是全局上限**：`build_provider()` 每个请求都新建 `DeepSeekProvider`，而信号量原挂在**实例**上，于是「全局并发 4」退化成「单请求并发 4」；多个重接口（审查 / 修改稿 / 对比）并发时会各自开满，一起冲同一账户配额，触发限流与退避重试（`max_retries=3`，退避 2/4/8 s），表现为**整站卡顿**——与文档口径「全局模型并发信号量（进程内）」不符。
- **修复**：
  1. `CompareView.vue`：`afterId` 默认置空——进入该页即走「生成修改稿 + 二次审查」主线；确需比较两份既有报告时，由用户在下拉框手动选择；`watch(beforeId)` 清空 `afterId`，避免换初稿后沿用上一份初稿的修改稿而错配。
  2. `CompareView.vue`：**不再在进入页面时自动跑对比**——生成修改稿要连跑一次完整审查，自动触发会让「打开对比页」变成一次重模型任务。改为由用户点右上角「生成修改稿并对比」触发（按钮文案随状态切换；未生成时该按钮为主按钮）。

### 修复「网络或服务异常」：重任务前端超时过短（2026-10-11）
- **问题现象**：走到审查 / 修改对比等模型链路时，前端提示「网络或服务异常，请稍后重试。」，页面看起来「无法使用」。

## 全量代码审查与缺陷修复（2026-10-12）

对后端（api / core / engine / parsers / models / storage / reports / tasks）与前端（views / components / stores / api）做了一次全量通读审查：每条缺陷先构造输入复现、再修复、最后加回归用例锁定。新增 `backend/tests/test_regressions.py`（32 项）与 `frontend/tests/`（13 项）。

### 致命（崩溃）

- **`docx_parser.is_citation_span` 的 `set + str`**：`MATH_PREV + "%"` 中 `MATH_PREV` 是 `set`，只要「上标裸数字」前一个字符是标点或段首、后一个字符非空即抛 `TypeError`；该异常绕过 `registry.parse_document` 的 `ParseError` 兜底 → **上传直接 500**。中文论文「…方法有效。¹ 随后…」这种写法很容易命中。

### 高（结论错误 / 大面积误报）

- **参考文献标题要求完全相等**：标题检测本身接受「7 References」这类编号，但比对用 `text.lower() in REFERENCE_TITLES` → 带编号/全角括注的标题一律不认，整段引用对账失效，并报出**确定性**的 R-REF-01（全部引用悬空）+ R-REF-02（未识别到参考文献列表）。
- **参考文献条目要求编号后有空白**：`REFERENCE_ITEM` 结尾是 `\s+`，GB/T 7714 与 CNKI 导出的「[1]张三…」全部漏解析，触发同上两条误报。
- **多括号上标被整体丢弃**：`BRACKET_TOKEN` 拆分逻辑存在，但 `is_citation_span` 只接受单个方括号组，`tokens` 永远只有 1 个元素 → 「[1][2]」两条引用一起丢失。
- **对比接口不下发 `revision_status`**：真实状态映射只被拼进 `notes` 散文，前端 `CompareFinding.revision_status` 恒为 `undefined` → 修改稿每条都显示灰底「未自动改写」，「仍有 N 项需作者本人处理」横幅永不出现。
- **表体要素与「表格上方正文段」要素不可区分**：表体要素的锚点就是其上方正文段的段落序号，只看锚点会把正文段证据误当成「表内证据已消费」，该降级的结论没降级。新增 `Element.in_table` 标记。
- **`代表3个模型` 被判成「表3」引用**：`图|表 + 数字` 无边界，正文里「代表3个模型」「发表3篇」都会产生幻影 `R-FIG-01` 结论并抬高 `figure_references`。
- **整句陈述被当成题注**：「图 1 显示了…对比。」因 `setdefault` 抢占真实题注，导致题注与正文的样本量冲突**永远检不出来**。

### 中（静默错误）

- **R-DATA-02 把不同量纲百分比相加**：「训练集占 80%，验证集占 20%，其中训练集正类占比 5%」→ 报成 105%（确定性结论）。改为按「连续枚举」分组后再求和。
- **R-DATA-03 不支持百分比写法**：「97%（95% CI 88%–96%）」完全不检查；现补可选 `%`，单位混用时保守跳过。
- **R-DATA-01 比例口径过窄**：原「之和必须是 10 或 100」把有效写法「4:1:1」判为确定性不一致，而 2 段写法完全不检查。改为：= 10 或 100 通过；< 10 视为合法份数写法不报；> 10 且 ≠ 100 才判为自相矛盾；正则同时放宽到 ≥2 段。
- **超链接文本整段丢失**：只遍历 `w:p` 直接子节点，`w:hyperlink` 内的 run 全被忽略（纯链接段落连 `Paragraph` 都不产出）。改为递归展开包装元素。

### 过程中发现并解决的两个真问题
1. **简介字数两次超标**：首稿 432 字（超 44%），且文件里自标的「296 字」是错的；经脚本实测迭代到 **298 字**。字数限制必须机器实测，目测不可靠。
2. **表格在 LibreOffice 中溢出**：`python-pptx` 写入的列宽在 XML 里完全正确（0.85″ + 11.6″ = 12.45″ < 13.33″），但 LibreOffice 会重排/缩放**自选图形**（实测标题竖条 0.09″×0.52″ 渲染成 0.12″×0.77″）。改为**先生成 PNG 再嵌入**——图片渲染是确定的（同一份 pptx 两次渲染，图片页字节完全一致）。
   **并澄清一个假警报**：`render` 的光栅化页尺寸为 1280×720 pt，与幻灯片 960×540 pt 不一致，故 `_ppt_preview` 中"右列被裁"是**渲染假象**；对 PDF 本体做像素检测，最右强调色落在 **12.44″**（正是表格右边界），右边距 0.89″，**确认无溢出**。
