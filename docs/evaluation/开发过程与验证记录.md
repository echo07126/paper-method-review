### W3 评测结论（5 篇样本 / 24 条标准答案）
- 仅规则：检出率 **16/24 = 67%**、精确率 **100%**；自建样本 14/14（100%），真实样本 2/10（漏项集中在语义类 R-03/R-04/R-08/R-14/R-15）。
- 规则 + LLM：检出率仍 67%、精确率降至 **70%**（LLM 未补上语义漏报——被证据门控降级为“存疑”；同时新增 R-04/R-06/R-12/R-07/R-10 等误报）。
- 结论：当前 LLM 既未提升召回又损伤精确率，因此 W3 调优优先级调整为——
  1. **规则扩条目**：把「缺失描述型」检查确定性化（R-03 无划分说明、R-04 无基线、R-08 多重比较、R-14 无种子、R-15 无局限），预计可大幅提升召回；
  2. **要素词表补齐**：为基线、局限、多重比较、划分说明等补充要素，使证据门控能给语义判定挂锚点，避免误降级；
  3. **规则前置否决**：规则对某条目判定“通过”时，LLM 不得再报问题，用于收敛误报；
  4. 完成后再跑 `eval_ac.py --llm` 与 `consistency_check.py`，目标检出率与精确率均 ≥90%。

结论（重要）：**LLM 语义判定目前无法稳定达到目标**，确定性规则才是可信基座。已落地的达标做法：
- 规则覆盖扩展到全部条目（R-02/03/05/07/08/09/14/15 + 引用类），并对可判定条目输出 problem/pass；
- **规则前置否决**：规则判定“通过”的条目，LLM 不得报问题；
- **顾问模式**：LLM 结论一律降级为「建议/存疑」（不计入问题数），仅作人工复核线索；
- 引文验证（逐字引用 + 条目关键词闸门）用于把模型结论落到原文；
- 锚点定位按“信号所在段落”选取（R-03/08/14 取相关段、R-15 取末段），AC-3 从 62% 提升到 91%。
1. **规则扩覆盖（主路径）**：把 R-04 基线数量、R-08 多重比较、R-10 重复/方差、R-13 预处理、R-15 局限等改为「存在/缺失」确定性判定；
2. **LLM 定位调整为“建议”**：LLM 结论默认进入「存疑/建议」区，只有引文验证通过才计入 problem；
3. **清单判定准则对齐**：为每条清单写明「可判定标准」，无法客观判定的条目标注为 advisory，不计入 AC-2 分母；
4. 完成后重跑评测，目标检出率与精确率均 ≥90%。

### 工程加固（2026-09-22）：数据生命周期、配置隔离与门禁
- **运行期定期清理**：原来 `cleanup_expired` 只在应用启动时执行一次，服务连续运行超过会话 TTL（默认 2h）后过期数据不再回收，与「会话过期自动清除」的对外口径不符。新增 `app/storage/cleanup_task.py` 常驻协程（每 300s 一轮），在 `main.lifespan` 启动时先清一次、退出时优雅取消；同时把孤儿临时目录（进程被杀导致的泄漏）一并回收。
- **保留期下限生效**：`DATA_RETENTION_HOURS` 此前是死配置（全代码无引用）；现由 `cleanup_expired` 读取，实际保留期取 `max(SESSION_TTL_HOURS, DATA_RETENTION_HOURS)`，并新增 4 项单测覆盖「超保留期清理 / 存活会话保留 / 孤儿目录回收 / 常驻任务可取消」。
- **冒烟脚本配置隔离**：`api_check.py` / `demote_check.py` 原先只设 `os.environ`，而 `Settings` 的 `model_config.env_file` 在类定义时固化为 `backend/.env`，导致 `.env` 覆盖环境变量——冒烟实际写入**真实 `./data`（含论文正文）**，且 `CHECKLIST_DIR` 被覆盖后脚本直接失败。修复：`core/config.py` 新增 `set_settings_override()` 注入点，脚本派生 `env_file=None` 的子类构造隔离实例并全局注入，末尾再断言真实 `data/` 未被写入（自证）。
- **门禁从"看得见"变成"拦得住"**：`security_audit.py` 原先只打印、退出码恒为 0；现已改为失败返回 1，并新增 3 项检查（常驻清理任务、保留期配置生效、孤儿目录回收），合计 **27 → 31 项，全部已实现**。
